# 关键决策

本文记录影响正确性、隐私与可维护性的设计选择，以及被放弃的替代方案。

## 1. 金额一律用整数分

**决策**：所有金额字段为 `Cents = number` 的整数，输入解析、展示、CSV、备份校验都围绕整数分。

**理由**：浮点累加会产生 `0.1 + 0.2` 类误差，现金流预测会放大误差并导致余额守恒断言不稳定。整数分让「余额 = 期初 + 流入 − 流出」可精确验证。

**代价**：UI 输入需要解析与格式化；百分比/分配需要显式取整。分配采用确定性余数分配，避免随机性。

## 2. 日期使用本地 ISO 字符串，解析锚定中午

**决策**：`ISODate` 为 `YYYY-MM-DD`；`parseISODate` 使用本地时间中午 12:00。

**理由**：中国时区下 `new Date('YYYY-MM-DD')` 按 UTC 解析，可能在前一天晚上显示为前一天；锚定中午避免夏令时/时区边界跨日。日期运算统一走 `days.ts`，不直接对 Date 做加减。

## 3. 同一预测引擎服务所有场景

**决策**：总览、预测页、目标 24 个月推演、消费沙盘全部调用 `runForecast`；沙盘通过 `scenario.purchases/reserves` 注入虚拟事件，不写入账本。

**理由**：如果每个页面各写一套预测，口径会漂移。统一引擎让「预测页看到的余额」与「沙盘里的基准路径」严格一致，也让校准与回测有唯一对象。

**代价**：沙盘需要把「购买消耗预留」表达为 `consumeReserved`，预测引擎需要理解预留增量与购买扣减的先后语义。

## 4. 可变消费采用「可降级、可解释」模型

优先级：

1. 最近 6 周同星期中位数（该星期至少 3 个样本且覆盖区间内）；
2. 月可变预算 ÷ 当月天数；
3. 覆盖日日均；
4. 未估计（`null`），绝不当作 0。

**理由**：年轻用户的消费具有明显星期效应；历史不足时用预算比编造历史更诚实。`null` 在 UI 中显示「未估计」，避免把缺数据伪装成零消费。

## 5. 同日收支按「支出先于收入」保守检查

**决策**：日终余额按净额计算，但额外输出 `coverageRisks`：若当天先付固定支出会导致余额跌破安全线、而当天收入到账后又恢复，仍提示覆盖缺口。

**理由**：只给日终余额会掩盖「工资当天到账但房租上午扣款」的短期缺口。保守检查不改变日终余额，只增加风险提示。

## 6. 逾期支出的不对称处理

- 逾期未核销**支出**：按今日待付计入预测，并写入假设说明；
- 逾期未核销**收入**：不默认到账。

**理由**：把未收到的钱当已到账会高估支付能力；把未付的固定支出忽略会低估风险。两者都保守。

## 7. 计划与流水分离，只有核销才产生流水

**决策**：计划是规则，期次是推导结果；核销才写真实交易。已核销期次不因计划编辑而改写；编辑支持「从下一期起」拆分。

**理由**：历史不可变，未来可调整。直接生成未来日期流水会污染账本，也无法表达跳过/改期。

## 8. 目标预留是 earmark，不是转账

**决策**：预留/释放只写 `GoalFundEvent`，不改变账户余额；「消费」才写真实支出并消耗预留。可自由支配金额 = 余额 − 总预留 − 安全储备。

**理由**：用户的目标资金通常仍留在工资卡/余额宝里。把它建模成账户转账会产生虚假的账户余额变化；earmark 更贴近真实心理账户，也让「最大可预留」有明确公式。

## 9. 分阶段预留采用「先看自由余额，再按节奏预留」

**决策**：`buildReserveSchedule` 从今天起按周/月节奏检查自由余额，能留多少留多少，累计到价格即完成；若自由余额一次足够，可能当天完成。

**理由**：这是对「不牺牲安全储备」的保守模拟，而不是强制分期。它解释了为什么「分阶段」有时与「立即」接近：当现金充足时，分期没有额外收益。

## 10. 沙盘中的购买与预留

- 立即/延期：购买日扣减余额；若关联目标，同时消耗不超过价格的已有预留，避免「预留已扣可支配金额、购买再扣一次」的双重扣减。
- 分阶段：预留日增加预留（降低 free，不改变 balance）；购买日扣减价格并消耗累计预留。

## 11. 数据本地优先、双库隔离

**决策**：Dexie 两个数据库（personal / demo），Zustand 只持有当前模式的内存快照；所有写操作通过事务批量提交。

**理由**：演示数据不能污染个人账本；切换模式要快；事务保证多实体更新（转账、核销、消费）不会半写。`navigator.locks` 串行化写，`BroadcastChannel` 让多标签页刷新。

## 12. 示例数据确定性与「今天」锚定

**决策**：固定种子 `20261124`；以运行日为锚生成 180 天历史；62 个快照由真实引擎生成；跨天检测 `meta.demoDate` 后重建。

**理由**：演示需要可复现，但日期必须贴近用户当天，否则「未来 30 天」全是过去。快照必须由真实引擎产生，校准与回测才有意义。

## 13. 备份导入「先校验、后预览、再覆盖」

**决策**：`validateBackupText` 在内存中完成 JSON 解析、Zod 结构校验、金额整数/非负、引用完整性、日期范围与模式检查；校验通过才显示恢复按钮。

**理由**：导入是最容易破坏账本的操作。先校验可以把损坏文件挡在写入之前，并让用户看到将覆盖什么。

## 14. CSV 只导出不导入

**理由**：CSV 字段模糊（日期格式、正负号、分类映射），静默猜测会污染账本。需要迁移时使用 JSON 完整备份。

## 15. 路由使用 HashRouter

**决策**：`HashRouter`，静态托管无需服务器重写规则。

**理由**：本地优先应用可能被放在任意静态目录；HashRouter 避免刷新 404。Qoder Sites 仍开启 SPA fallback 作为额外保险。

## 16. ECharts 按需引入但仍体积较大

**决策**：直接使用 `echarts` 完整包与 `echarts-for-react` 风格的本地封装。

**代价**：主包约 1.8 MB（gzip 约 583 KB），构建有 chunk 体积警告。若后续优化，可改为按图表类型注册 ECharts 模块并动态加载。

## 17. 错误与限制显式呈现

**决策**：预测页展示假设、覆盖率、来源、校准状态；洞察展示证据与阈值；沙盘展示「未建模事件」；数据中心展示覆盖不足与回测样本。

**理由**：这类产品最大的风险是「看起来精确」。把不确定性写进界面，比在文档里补一句免责声明更有效。
